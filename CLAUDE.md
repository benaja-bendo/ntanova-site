# ntanova-site

Le site de NTanova : l'annuaire public des écoles de la République du Congo (**Congo-Brazzaville, pas la RDC**), l'espace des relais qui relèvent les écoles sur le terrain et l'administration, poste de pilotage du catalogue. Dépôt privé `benaja-bendo/ntanova-site`.

**Périmètre confirmé par le fondateur le 04/11/2026 : les relais peuvent collecter partout au Congo-Brazzaville**, sans se limiter à Tié-Tié, Ngoyo, un lot ou une zone dite ouverte. Le fondateur décide dans son tableau de bord de ce qui est prêt à être publié. Collecter, accepter et publier restent distincts ; aucune publication automatique ne découle d'une collecte. Les secteurs conseillés, `geo_divisions.open_for_fieldwork` et les états publics de déploiement ne doivent pas être interprétés comme des interdictions de collecte. Ces paramètres existent dans le code ; cette consigne ne prétend pas que tous les écrans et guides sont déjà alignés.

Ce dépôt ne contient que le code. La stratégie, les hypothèses et les seuils vivent ailleurs, dans un dépôt privé : **n'en recopier aucun ici**, ni dans le code, ni dans les commentaires, ni dans les commits.

## Lancer

```bash
nvm use                # Node 24 (.nvmrc)
pnpm install
cp .env.example .env   # puis compléter les valeurs publiques
pnpm dev               # http://localhost:4321
```

Le catalogue du système de design : http://localhost:4321/dev/catalogue/ (en développement seulement).

## Vérifier

- `pnpm verif` : format, lint (dont les frontières), couleurs, types, tests unitaires, construction, poids des pages. **Rien n'est fini tant qu'elle ne passe pas.** La construction exporte le guide du relais (PDF et images) : il faut le Chromium de Playwright (`pnpm exec playwright install chromium`). La CI lance `pnpm verif:ci` : la même vérification avec le catalogue fictif complet, construit et pesé une seule fois pour les parcours.
- `pnpm test:parcours` : les parcours Playwright, dans un téléphone Android de 360 px, sur le site construit servi par wrangler comme en production. La spec `mise-en-page` (les tests qui dépendent de la largeur : barre de l'administration, tableaux, défilement de côté…) tourne aussi à 768 px (tablette) et 1 280 px (ordinateur). **Le port de `wrangler dev` est 4329, ou `PLAYWRIGHT_PORT`** : deux suites sur un même Mac ne peuvent pas partager le même : donnez un port différent à la seconde (`PLAYWRIGHT_PORT=4411 pnpm test:parcours`). **Depuis deux clones différents** : deux suites du même clone se piétinent dans son dossier `test-results/`.
  Le site y est construit avec le **faux serveur** (`PUBLIC_ADAPTATEUR=faux`, `src/infra/faux/`) : l'espace relais tourne sans Supabase, hors ligne compris. Le parcours « trois fiches hors ligne, le réseau revient, tout est parti, le contact a disparu du téléphone » ne doit jamais être affaibli.
- Pendant le développement : `pnpm test:parcours:preparer`, puis `pnpm test:parcours:exec tests/parcours/<ticket>.spec.ts`. Reconstruire avec `preparer` après toute modification applicative ; `exec` sert à répéter des tests sur ce même site, jamais à vérifier un ancien build après changement du code. La suite complète reste `pnpm test:parcours`.
- CI : deux lots Playwright équilibrés, cas isolés répartis entre machines (`fullyParallel`), un worker par machine. `node outils/verification-ci.ts partitions` contrôle que leur union couvre tous les parcours, sans perte ni doublon. Le verdict global est **Validation complète** : `verif` seul ne suffit pas. Un lot absent/annulé/en échec bloque cette validation. Rapports `rapport-parcours-1/2`, preuve `verification-complete` produite seulement après format/types/unitaires/construction/poids, les deux lots et SQL réussis. Le temps global des parcours est borné à 12 min pour laisser le job de 15 min sauvegarder son rapport.
- `pnpm captures` : une image de chaque écran (site public, relais, administration) à 360, 768, 1 280 et 1 920 px, dans `captures/` (ignoré par git), pour relire une mise en page à l'œil. Elle ne vérifie rien.
- `pnpm base:tests` : les tests pgTAP des droits et des règles de la base (`supabase/tests/`), sur la base locale (`pnpm base:demarrer`, Docker). La CI les lance aussi. Sans Docker (session cloud) : `supabase/portabilite/banc.sh verifier` rejoue les migrations sur un PostgreSQL jetable, lance les mêmes tests, puis prouve que la base se restaure sur un PostgreSQL ordinaire.
- **Le contrat avec la base** (`tests/unitaires/contrat-schema.test.ts`) : tout ce que `src/infra/supabase/` appelle (fonctions et paramètres, tables, vues, colonnes, liens) doit exister dans les migrations. Les parcours tournent sur un faux serveur : sans ce test, un nom de colonne faux ne se verrait qu'en production. **Toute migration qui renomme ou retire quelque chose change l'adaptateur dans le même commit.**

## Architecture

```text
src/
  modele/      schémas Zod, listes fermées, règles pures, ports.ts (les contrats)
  infra/       seul dossier qui connaît Supabase : supabase/, et index.ts qui branche l'adaptateur
  app/relais/  React : écrans, base locale (Dexie), file d'envoi ; n'appelle que les ports
  app/admin/   React : À valider, Relais ; n'appelle que les ports
  app/commun/  ce que partagent relais et admin : connexion Google, navigation par le dièse
  pages/       Astro : site public (lit le catalogue à la construction : lieux, fiches, renvois, plan du site, recherche), coquilles /relais et /admin
  ui/          jetons (variables CSS) et composants, sans appel réseau
  worker/      le compteur /go/ (Cloudflare Worker)
supabase/      migrations SQL, règles d'accès, tests pgTAP, données fictives
tests/         unitaires (Vitest), parcours (Playwright)
outils/        contrôles maison (couleurs, poids), import des écoles du Sheet (JSON pour l'administration), rues d'OpenStreetMap, export du guide du relais (PDF et images)
```

Les frontières sont **gardées par ESLint** (`eslint.config.js`), et la règle elle-même par `tests/unitaires/frontieres.test.ts`. Ne jamais l'affaiblir pour faire passer un import : changer l'import.

- `@supabase/*` ne s'importe que dans `src/infra/`.
- `src/app/` et `src/pages/` reçoivent les adaptateurs par `src/infra/index.ts`, jamais par un fichier de `src/infra/supabase/`.
- `src/modele/` reste en TypeScript pur : ni React, ni `infra`, ni `ui`.
- `src/ui/` ne fait aucun appel réseau.
- L'espace relais et l'administration ne dépendent pas l'un de l'autre ; ce qu'ils partagent vit dans `src/app/commun/` (sans appel à `infra` autre que par les ports) ou `src/ui/` (composants React sans réseau, `src/ui/composants.tsx`). La règle d'ESLint reconnaît un dossier `relais` ou `admin` à son nom : un fichier de l'administration ne s'appelle pas `Relais.tsx`.
- Des fonctions simples plutôt que des classes ; aucun outil d'injection de dépendances.

### Les ports, nommés d'après les routes qu'ils deviendront

Le jour où un serveur (Spring Boot) remplacera Supabase, seul `src/infra/` sera réécrit en appels REST.

| Port | Opérations | Route future |
| --- | --- | --- |
| Catalogue public (à la construction) | Lister les divisions (du pays au quartier), les campus publiés avec leurs cycles et leurs formations, les domaines, les renvois des anciennes adresses | `GET /public/divisions`, `GET /public/ecoles`, `GET /public/domaines`, `GET /public/renvois` |
| Session | Se connecter avec le jeton Google, se déconnecter, lire l'utilisateur courant, obtenir un jeton frais | `POST /auth/google`, `GET /moi` |
| Relais | Mon profil, mon secteur (son lot, facultatif), les zones ouvertes, mes relevés et leurs retours, les écoles qu'on me confie ; envoyer une photo, un relevé, un contact, une erreur | `GET /moi/lot`, `GET /zones-ouvertes`, `GET /moi/releves`, `GET /moi/ecoles-a-completer`, `PUT /photos/{chemin}`, `POST /releves`, `POST /contacts`, `POST /erreurs` |
| Administration (`PortAdministration`) | Le rôle ; les relevés à valider, leur détail, **leurs photos côte à côte**, leur contact ; accepter **en un geste (nouvelle école, nouvelle implantation, mise à jour, nouveaux niveaux) avec les formations lues sur les photos**, demander une correction, refuser, confirmer un contact ; **le pont avec la direction** (premier message, accord daté) ; les relais, **le journal des téléphones (« Santé des envois »)**, les lots, **les zones** (ouvrir, ajouter) ; les écoles : les corriger, les confier à un relais (mission), les situer, **en créer ou en importer une liste (simulation d'abord)**, publier, retirer, fusionner ; **la paie du vendredi** | `GET /admin/releves`, `GET /admin/releves/{id}`, `POST /admin/releves/{id}/decision`, `GET /admin/releves/{id}/photos`, `GET /admin/relais`, `GET /admin/erreurs`, `POST /admin/relais/{id}/activation`, `GET /admin/zones`, `PUT /admin/zones/{id}/ouverture`, `POST /admin/lots`, `GET /admin/ecoles`, `PATCH /admin/ecoles/{id}`, `POST /admin/ecoles`, `POST /admin/ecoles/import`, `POST /admin/ecoles/{id}/confier`, `PUT /admin/ecoles/{id}/position`, `POST /admin/verifications`, `GET /admin/paie`, `POST /admin/paie/{vendredi}/cloture` |

- **Chaque envoi porte un identifiant créé sur le téléphone** et répond « reçu » ou « déjà reçu ».
- **Relevés et photos** : `.insert()` sans `.select()`, photo sans écrasement. Un second envoi du même identifiant renvoie une erreur de doublon (code `23505`, ou 409 pour la photo), que l'adaptateur traduit en « déjà reçu ». Jamais d'`upsert`.
- **Contacts** : par la fonction `send_contact()`, qui répond `recu` ou `deja_recu`. La table vit dans le schéma `prive`, que l'API n'expose pas : le relais ne peut pas la relire.
- **L'ordre d'envoi d'une fiche** : le relevé, puis le contact, puis ses photos (chacune rejouable). Le contact ne dépend pas des photos : une photo qui ne part pas ne l'arrête plus (ticket #94).
- **La file d'envoi (`src/app/relais/file-envoi.ts`) ne se bloque jamais et le dit** (ticket #74, essai du fondateur sur iPhone). **Une fiche dont l'envoi échoue ne retient pas les suivantes** : une erreur de connexion alors que le téléphone se dit en ligne compte un essai sur cette fiche (`dernierEchec`, `essais`), garde l'étape et la raison, est écrite dans le journal (`reseau_<étape>` : message du navigateur, « en ligne », taille de la photo) et la file passe à la suivante ; seul un téléphone qui se dit hors ligne (`navigator.onLine`) arrête la file. Avant, la première erreur de ce genre faisait `return 'hors_ligne'` : les fiches suivantes n'étaient jamais essayées, le journal n'était jamais envoyé, et l'écran ne disait rien. **Chaque appel a une limite de temps** (`avecDelai` : 30 s, 60 s pour une photo) et l'ensemble aussi (`limiterLeTemps`, 150 s) : « un seul envoi à la fois » ne peut plus attendre pour toujours un envoi suspendu. **« Envoyer maintenant » montre qu'il travaille** (« Envoi en cours… » avec la roue) **puis dit le résultat** (`phraseDuBilan` : « Un envoi a échoué (3 h 39) : la photo de « X » n'est pas partie », ou les fiches parties) ; chaque fiche en échec le dit dans « Mes fiches » (`phraseDEchecDeLaFiche`).
- **Les photos partent de la mémoire, jamais du fichier de la base du téléphone** : la file lit les octets de chaque photo (`lireLesOctets`) **avant** tout envoi, puis le stockage reçoit ces octets en corps brut (`PhotoPrete.contenu`). Sur iPhone, envoyer directement le fichier relu dans IndexedDB (en multipart) échoue (« Load failed ») sans qu'une requête parte, et l'échec ressemblait à une panne de réseau : **aucun envoi de photo depuis un iPhone n'est jamais arrivé** dans les journaux avant le 03/11. Une photo qui ne se relit plus (vide, illisible) est dite : l'enseigne exigée arrête la fiche **avant** son relevé avec sa raison (`photo_illisible`), une autre photo est laissée de côté et le journal le dit. Un parcours ne simule jamais cela avec un fichier : il vide la photo dans la base du téléphone (`tests/parcours/envoi-visible.spec.ts`).
- **Les photos d'une fiche** : l'enseigne seule est obligatoire ; trois autres au plus (panneau des formations, prospectus, vue du bâtiment, **jamais d'enfant**). Chacune est **allégée dans le téléphone à moins de 200 Ko** (WebP, sinon JPEG ; on baisse la qualité, puis la taille ; une photo qui ne passerait jamais est refusée, jamais gardée trop lourde). **Fiches et photos vivent dans IndexedDB (Dexie), jamais dans `localStorage`** (`tests/unitaires/hors-ligne.test.ts` le garde). Le cache local des écoles connues (toutes les zones ouvertes, plus le secteur du relais s'il en a un) fait marcher l'alerte « une école est déjà relevée à 40 m » **sans réseau**, où que le relais se trouve.
- **Session** : le jeton expire au bout d'une heure et ne se renouvelle qu'avec du réseau. Le port fournit un jeton frais à la file d'envoi ; un relais saisit même avec une session expirée et se reconnecte sans rien perdre. Le rôle (relais actif, administrateur) vient de la base, pas de Google.
- **Un téléphone peut servir à deux relais** (ticket #55, PR 6) : chaque fiche du téléphone porte le `compteId` du relais qui l'a commencée (`src/modele/compte.ts`, base du téléphone en version 4). La file d'envoi, « Mes fiches », « Mon secteur » et le brouillon ne voient que les fiches du compte connecté ; **une fiche ne part jamais sous le nom d'un autre relais** (la paie irait au mauvais). « Se déconnecter » (onglet « Compte ») **ne supprime aucune fiche** : elle prévient de ce qui reste sur le téléphone, et l'écran de connexion le redit. Un changement de compte efface ce que le téléphone gardait du serveur pour l'ancien (son secteur, ses fiches reçues, sa paie), jamais ses fiches non envoyées. Il n'y a **qu'un brouillon par compte**, retrouvé d'après la fiche (plus de repère `brouillon` dans la mémoire). Les versions de la base du téléphone se suivent sans trou : une PR qui en ajoute une le dit sur le ticket avant de pousser.
- **L'application installable se limite à `/relais/`** : son cache ne touche ni le site public ni l'administration.

### Ce qui vit dans la base (`supabase/`)

La carte des tables, des droits et des fonctions : [`supabase/schema.md`](supabase/schema.md).

- Les contraintes, les déclencheurs (doublon possible à moins de 40 m, hors du lot au-delà de 50 m du contour, heure de réception donnée par le serveur, adresse publique à un seul propriétaire) et les vues (campus publiés, relevés à valider, compteurs par relais, statistiques par zone). Ce sont les règles qui doivent survivre à un changement de serveur.
- **Structure en anglais, vocabulaire en français** : tables, colonnes et fonctions de la base sont en anglais (`geo_divisions`, `campuses`, `accept_submission`) ; les ports (`src/modele/ports.ts`) et l'interface sont en français ; **seuls les adaptateurs de `src/infra/supabase/` traduisent**. `relais`, `lots`, `echanges`, `erreurs` et `prive` gardent leur nom.
- **Portable** : le cœur de la base (`public`, `prive`) ne dépend de rien de Supabase (extensions `postgis`, `pg_trgm`, `unaccent`, `ltree` ; identité par `current_user_id()`). Ce qui est propre à Supabase est dans `20261101200900_supabase_couche.sql`. Le guide pour sortir de Supabase : `supabase/schema.md`, « Sortir de Supabase ».
- Les règles d'accès (RLS) sur chaque table.
- **Des `grant` explicites** : en ligne, une table créée par `postgres` ne donne rien à `anon` ni à `authenticated` ; en local, Supabase leur donne tout. Chaque migration qui crée une table, une vue ou une fonction retire donc d'abord les droits, puis donne exactement ceux qu'il faut (voir `20261031010200_droits.sql`). Le relais n'a le droit d'écrire que les colonnes remplies par le téléphone.
- **Les lots fins** (ticket #49, `supabase/schema.md`, « Les lots fins ») : une division se coupe en lots par une migration de données qui utilise `ST_Split`, rattache les relevés (`prive.attach_submissions_to_fine_lots`) et se vérifie avec `prive.lot_problems`. **Le lot est un secteur conseillé, jamais une barrière** (ticket #67) : **la collecte est autorisée partout au Congo-Brazzaville** (clarification du fondateur, 04/11/2026), y compris hors des zones dites ouvertes ; la publication reste une décision de l’administration. « Hors du lot » (à plus de 50 m du contour) n'est qu'une information, calculée par la base à l'arrivée du relevé (`outside_batch`) : le téléphone ne la calcule plus ni ne la montre, et ni le refus d'une fiche ni la paie ne la lisent. La base dit aussi, à l'arrivée, la division de la position (`division_id`) et si elle est ouverte (`in_open_zone`, nul quand aucun contour connu ne la contient : « zone inconnue » n'est pas « hors zone »). Un relais peut n'avoir aucun lot (`activer_relais(relais, null)`). **Un lot se pose sur une zone ouverte aux relais** (`create_lot` refuse une zone fermée, sauf lot d'entraînement). Ne pas confondre la contre-visite de l'application (un type de relevé) et la « contre-visite de lot » (un contrôle fait à la main, hors de l'application).
- **L'état d'une zone sur la carte se règle dans l'administration** (onglet « Zones », volet de la zone ou vue « Par étape », ticket n° 131) : « Pas encore couverte », « Déploiement programmé » ou « Relevé en cours » (`public_status`, fonction `set_division_public_status`). C'est **distinct de l'ouverture aux relais** (`open_for_fieldwork`, interrupteur « Ouverte aux relais ») : les relais peuvent relever partout au Congo-Brazzaville (04/11/2026) ; changer l'état de la carte ne change rien pour eux. Le site étant statique, un changement n'est visible qu'après une mise en ligne.
- **Le site public n'écrit plus cet état** (décision du fondateur du 08/11/2026, qui revient sur D2 de l'audit du 05/11 ; ticket 146) : ni la carte (toutes les zones du même dessin, nom seul, plus de légende), ni les pages de lieu, ni `/ecoles/`, ni l'accueil. **Le réglage décide encore quelles zones la carte dessine** (`zonesGeoJSON` : une zone sans état n'y est pas) **et où elle s'ouvre** (`cadrage.ts` préfère une ville qui a une zone « relevé en cours ») ; `etatPublicDe` et `libelleDeploiement` (`src/modele/etat-zone.ts`) ne servent plus qu'à cela et à l'administration, dont les textes le disent (`explicationEtat`, `ZonesEtapes.tsx`, `ZonesVolet.tsx`). Une zone qui a son état a sa page même sans école (`construireArbre`), pour que chaque lien de la carte mène quelque part (Brazzaville) ; cette page est en `noindex` et hors de `sitemap.xml` tant qu'elle n'a pas de fiche. Tests : `etat-zone.test.ts`, `donnees-carte.test.ts`, `etats-de-zone.spec.ts`.
- **Appels à l'action des directions** : deux verbes, selon le cas. **« Confirmer »** quand la fiche existe (accueil : « Confirmer la fiche de mon école » ; fiche : « Confirmer cette fiche », un lien WhatsApp qui porte déjà le nom de l'école et l'adresse de sa fiche). **« Ajouter »** quand elle n'existe pas (« Ajouter mon école »). Un seul bouton plein sur `/pour-les-ecoles/` (« Écrire sur WhatsApp ») ; le code de la fiche de liaison est dans un `<details>`. Plus de « référencement » dans les textes publics.
- **Les listes fermées sont des domaines SQL**, copiés dans `src/modele/listes.ts` : un test vérifie qu'ils restent identiques. **Une liste ne bloque jamais personne** (ticket #12) : toujours une case de sortie (`autre`, `non_indique`), rien d'obligatoire ni coché d'avance si cela fausse la donnée, un texte libre facultatif (`programme`) pour ce que la liste ne sait pas encore, l'administration qui corrige sans repasser par le relais, des lectures tolérantes (`typeConnu`, `niveauxConnus` : une valeur inconnue se lit « Pas indiqué » ou se laisse de côté, jamais d'erreur). **On ne retire et on ne renomme jamais une valeur** (pour changer un mot, on change le libellé).
- **Ajouter une valeur à une liste** : 1) une migration `alter domain … drop constraint`, puis `add constraint … check (value in (…)) not valid` (**`not valid` obligatoire** : `niveaux` est un tableau, que PostgreSQL ne sait pas revalider) ; 2) `src/modele/listes.ts` ; 3) `src/modele/libelles.ts` ; 4) `pnpm verif` ; 5) `pnpm exec supabase db push` **avant** la mise en ligne. Le détail : [`supabase/schema.md`](supabase/schema.md), « Les listes ».
- **Le lot d'essai ne colle plus à une fiche qui n'en est plus** (05/11/2026, migration `20261105140000`) : le téléphone envoie le lot qu'il a lu un jour (`batch_id`), et un relais sorti de l'essai (« Sans lot ») envoyait encore des fiches « du lot d'essai », que la base refuse ensuite d'accepter et de publier (« Relevé du lot d'essai : il ne se publie jamais »). À l'arrivée, le déclencheur remplace un lot d'essai qui n'est plus celui du relais par son lot actuel, nul s'il n'en a pas ; un autre lot envoyé reste tel quel. **Un nouveau relais n'est plus proposé sur le lot d'essai** à l'activation (`ListeRelais.tsx`) ; le lot d'essai reste dans le menu. Les fiches **déjà arrivées** du lot d'essai ne bougent pas (le déclencheur ne tourne qu'à l'arrivée) : une fiche bloquée se sort de l'essai à la main, en changeant son `batch_id`. Les tests (`lot_essai_perime.test.sql`) ; ceux de la paie et des lots qui posent des fiches d'essai pour des relais hors essai les replacent dans le lot d'essai par un `update`.
- Les relais sont liés à leur compte Google (l'identifiant `sub`), pas seulement à leur identifiant Supabase.
- **Les photos : des chemins relatifs, jamais une adresse de serveur** (`<relevé>/<photo>.webp` dans le seau `releves`) ; une contrainte de la base refuse tout ce qui ressemble à une adresse. Une photo est **privée** tant que l'administration n'a pas vérifié qu'elle est publiable (sans enfant ni donnée personnelle) : un prospectus peut porter le nom d'un directeur. **Le relais relit les photos de SES relevés, et seulement elles** (`my_submission_photos` et la règle du seau, ticket #72) : en corrigeant une fiche, il voit ce que NTanova a reçu. Il ne lit jamais la table des photos, ni les fichiers d'un autre relais.
- Des données d'exemple **fictives** seulement. Les vraies écoles connues par les entretiens entrent par `node outils/importer-ecoles.ts <export.csv> > import.json`, puis l'administration (onglet « Écoles », « Ajouter ou importer des écoles », « Une liste ») qui vérifie en simulation avant d'écrire : le CSV et le JSON réels ne passent jamais par git.
- **Jamais de position inventée** : une position vient d'un relais sur place, ou de l'administration qui connaît l'école et la prend sur une carte (`locate_campus`, `create_catalog_entry`, décision du fondateur le 31/10 ; la base garde qui et quand : `located_by`, `located_at`). **Elle se saisit aussi sur la fiche « À valider »** quand le téléphone du relais n'a pas pu la mesurer (ticket 144, `accept_reviewed_submission(…, p_latitude, p_longitude)`, `peutSaisirLaPosition` dans `src/modele/acceptation.ts`) : jamais pour une fiche qui a déjà la sienne, la position du relais fait foi. Sinon l'école reste « à situer ». Une fiche qu'aucun relevé n'a décrite dit « Fiche ajoutée par NTanova le … », jamais « relevée par un jeune du quartier ».
- Les migrations s'appliquent depuis le Mac du fondateur (`pnpm exec supabase db push`), après relecture, **avant** la mise en ligne du code. Jamais depuis la CI pour l'instant.
- **Deux lignes rouges du fondateur** : la confiance n'est pas à vendre (le badge « Vérifié par la direction » ne s'achète jamais et ne s'écrit qu'avec un accord daté ; une information factuelle ne se modifie pas contre paiement) ; et NTanova n'encaisse jamais les frais de scolarité (la paie ne concerne que les relais).

## Secrets

- Dans le navigateur, **seulement la clé `publishable`** de Supabase. Aucun composant en ligne n'utilise la clé `secret`.
- Les variables publiques passent par `astro:env` (schéma dans `astro.config.mjs`) et commencent par `PUBLIC_`.
- `.env` n'est jamais commité ; `.env.example` ne contient que des valeurs publiques.
- GitHub : deux secrets seulement, `CLOUDFLARE_API_TOKEN` et `CLOUDFLARE_ACCOUNT_ID`.
- Le mot de passe de la base et la clé `secret` restent dans le gestionnaire du fondateur. Ne jamais les demander, les afficher ni les écrire dans un fichier.

## Système de design

- **Du CSS simple**, sans Tailwind. Les jetons sont dans `src/ui/jetons.css`, **seul fichier où une couleur s'écrit en valeur** (`pnpm couleurs` refuse les autres). Les composants utilisent les jetons de rôle (`--fond`, `--texte`, `--marque`, `--etat-…`), pas les couleurs de base.
- Les classes de composants (`.bouton`, `.champ`, `.etiquette`, `.etat-verifiee`…) sont dans `src/ui/composants.css`, partagées par Astro et React.
- **Texte courant à 16 px.** Échelle : 12, 14, 16, 18, 22, 28 px (`--taille-…`).
- **Polices servies par le site** (`public/polices/`) : Poppins 700, Nunito Sans 400 et 700. Jamais Google Fonts ni un autre service extérieur.
- **Cibles** : 48 px pour les actions principales, 44 px au moins partout, 8 px entre deux cibles.
- Thème clair d'abord : on lit l'écran dehors, en plein soleil.
- Chaque nouveau composant entre dans le catalogue (`src/pages/dev/[page].astro`), dans chacun de ses états : normal, focus, désactivé, erreur, chargement.
- Le code est la source du système de design ; l'artefact de design n'en est qu'une copie.

### Santé des envois (ticket #77)

- **Le journal des téléphones se lit dans l'administration** (onglet « Santé des envois », `src/app/admin/Sante.tsx`), plus par SQL : la table `erreurs`, déjà lisible par l'administration (aucune migration), regroupée par relais, signal, version de l'application et appareil (`src/modele/sante.ts` : `regrouper`, `expliquerCode`, `appareilLisible`).
- **Un code, une phrase** (`expliquerCode`) : jamais un mot de la base ni du navigateur. **Un code que le fichier ne connaît pas s'affiche tel quel** (« Signal inconnu : … ») : un nouveau signal du téléphone ne casse jamais l'écran. **Quand le téléphone écrit un nouveau code, on ajoute sa phrase dans `PHRASES`.**
- **La période par défaut est de 7 jours** : le bruit d'une nuit de bascule (des téléphones d'avant la mise à jour qui lisent des tables renommées : 164 lignes sur 193 le 02/11) sort de la vue sans aucun filtre écrit en dur ; « Tout » le rend, expliqué comme « ancienne version de l'application ».
- La lecture passe par `toutesLesLignes` : le plafond de 1 000 lignes de l'API ne tronque jamais le journal en silence.
- **Dans le détail d'une fiche à valider** (`SignauxDuRelais`) : ce que le téléphone de CE relais a signalé ces 7 derniers jours (trois signaux au plus, un lien vers tout le journal) ; rien d'affiché quand il n'a rien signalé, et une lecture qui échoue ne bloque jamais la décision.

### Une décision dit toujours quoi faire (ticket #80)

- **Avec le motif « autre », le message de NTanova est obligatoire**, pour une correction comme pour un refus (un refus est définitif : il dit pourquoi). Sa phrase de repli (« Une information est à revoir. ») ne dit rien : un relais s'est déjà retrouvé renvoyé sans savoir quoi corriger. La règle est écrite **trois fois, identique** : `messageManquant` (`src/modele/decision.ts`, l'écran et le faux serveur), `request_correction` et `refuse_submission` (la base, `22023`, la même phrase). Un message d'espaces et de retours à la ligne n'en est pas un (côté base : `!~ '\S'`, car `btrim` ne retire pas les retours à la ligne).
- Les autres motifs gardent leur phrase automatique (`libelleMotif`) : le message y reste facultatif. Une ancienne ligne « autre » sans message se lit toujours (lecture tolérante) ; rien n'est réécrit. « Refuser » propose « autre » par défaut : il faut donc un message.

### La photo publique d'une école (raccord du 07/11/2026)

- **Trois modes, lus dans la base** (`etatPhotoPublique` → `campus_public_photo_state`, jamais déduits côté écran) : *automatique* (aucun choix : la première enseigne ou vue du bâtiment **contrôlée** d'un relevé accepté d'une fiche publiée), *choix* (une photo prioritaire) et *retire* (retrait explicite : aucun repli, même si d'autres photos sont contrôlées). `decrirePhotosPubliques` (`src/modele/photos-publiques.ts`) écrit les phrases ; une candidate contrôlée n'est **jamais** présentée comme publique, seule la photo « retenue » (celle de la vue `public_campus_photos`, fiche publiée) l'est.
- **Contrôler pour publication** (« À valider », `marquerPhotoPubliable`) : seulement l'enseigne et la vue du bâtiment peuvent paraître (`ROLES_PUBLIABLES`). Le panneau des formations et le prospectus se contrôlent aussi mais **restent privés** et ne promettent rien de public. Contrôler ne publie rien : la photo devient candidate au repli, visible après acceptation, publication de la fiche et mise en ligne du site.
- **Retirer = `choisirPhotoPublique(ecoleId, null, false)`**, toujours : la base écrit un choix nul qui bloque aussi le repli. **Jamais** en retirant seulement le contrôle d'une photo (une autre photo contrôlée paraîtrait « par surprise »). Le bouton est offert dès qu'une photo contrôlée pourrait être retenue, pas seulement quand `is_public` vaut vrai. Après un retrait, un nouveau choix reste possible (il n'y a pas de commande « revenir à l'automatique »).
- **Corbeille et restauration ne publient aucune photo** : elles ne touchent ni les choix ni les contrôles ; une école restaurée est « prête », jamais « publiée », donc sans photo publique jusqu'à ce que l'administration la republie. Un retrait ou un choix traverse la corbeille. Le faux serveur le rejoue (`etatPhotoFaux`), `supabase/tests/photo_publique_administration.test.sql` et `tests/parcours/photo-publique.spec.ts` le gardent.

La carte ne revient plus après (`Memoire.premiersPas`, par compte). **Aucune version de la base du téléphone** : la mémoire clé-valeur suffit (`premiersPas`, et `testPhoto` le temps du test) ; la version 5 de Dexie reste réservée à la PR 7 du #55.

### La sauvegarde (ticket #81)

- **Le plan gratuit de Supabase ne sauvegarde rien** : `.github/workflows/sauvegarde.yml` fait chaque nuit une copie **chiffrée** (`age`) de la base (schémas `public` et `prive`, PostgreSQL 17) et des photos du seau `releves`, par `outils/sauvegarder-la-base.sh`, conservée 30 jours comme artefact privé. **Jamais un dump en clair hors d'un dossier temporaire**, jamais une clé ni une chaîne de connexion dans le dépôt : les quatre valeurs sont des secrets GitHub posés par le fondateur (`SAUVEGARDE_DB_URL` du « Session pooler », `SUPABASE_URL`, `SUPABASE_SECRET_KEY` (une clé secrète dédiée, pas l'ancienne `service_role`), `SAUVEGARDE_CLE_PUBLIQUE`). `tests/unitaires/sauvegarde.test.ts` garde le workflow (pas de `pull_request`, lecture seule, secrets par `secrets.*` seulement, seul un `.age` part) et le script (refus d'un dump vide, chiffrement avant écriture).

Ne jamais ajouter de `|| true` ni un saut silencieux « si le secret est absent » : une sauvegarde qui ne tourne pas ne doit pas se taire. ### Les comptes en attente (ticket #78)

- **Un relais naît « en attente » à sa première connexion Google ; l'administration le reconnaît à son adresse.** L'adresse de connexion est gardée **dans la partie privée** (`prive.relay_identity`, migration `20261103110200`) : aucun rôle de l'API ne la lit, ni un relais (pas même la sienne), ni un visiteur ; l'administration la lit par `relay_identities()` (`exiger_admin_session()`). Le cœur reste portable : le serveur d'identité donne l'adresse à `register_relay(id, sub, prénom, adresse)` ; l'ancien appel à trois paramètres marche toujours, sans rien garder. Le déclencheur de la couche Supabase la lui donne (`new.email`) et reprend **une fois** l'adresse des relais déjà inscrits (`supabase_layer.backfill_relay_identities()`, migration `20261103110300` : la lecture de `auth.users` ne vit que dans la couche).
- **L'écran « Relais »** montre l'adresse sous le prénom, met **les comptes à activer en premier**, propose « Activer » et « Écarter » (un inconnu passe « suspendu » et peut être réactivé), et **le menu porte un compteur** des comptes à activer (d'où qu'on arrive : l'accueil le lit aussi). L'écran ne demande plus d'ajouter une adresse dans Google Cloud ; une note repliée dit pourquoi quelqu'un ne peut pas se connecter (**tant que l'application Google est en mode « test »**, seules les adresses de ses utilisateurs de test le peuvent ; la publier lève la limite : action du fondateur, à vérifier dans la console Google).
- **Le relais en attente écrit lui-même** (`messageDActivation`, `CompteEnAttente`) : NTanova n'a pas son numéro et ne peut pas le « prévenir sur WhatsApp ». Le message dit l'adresse de son compte, rien d'autre.
- **Le code peut arriver avant `supabase db push`** : si la base n'a pas encore `relay_identities`, la liste des relais se lit quand même, sans adresses (`tests/unitaires/adaptateur-administration.test.ts`). Une adresse est une donnée personnelle (loi n° 29-2019) : elle ne quitte jamais `prive`, et son effacement passera par le journal `erasures`, comme les autres (pas encore écrit).

### Accepter une correction (ticket #89)

- **Le bouton « Accepter » ne se grise jamais sans dire pourquoi** (`ceQuiManquePourAccepter`, `src/modele/acceptation.ts`) : ce qui manque (la division, l'institution, l'implantation) s'affiche sous les boutons. Avant, une correction d'un relais **sans secteur** (la plupart) grisait le bouton, et le panneau où choisir la division était caché pour une correction : impasse.
- **Une correction d'une école déjà créée ne demande jamais de division** : elle met l'école à jour, qui a déjà la sienne (`divisionRequise`). **Une correction d'une fiche pas encore acceptée** (le relais qui reprend sa photo après un « à corriger ») **se traite comme une nouvelle fiche** : même panneau (nouvelle école, nouvelle implantation, mise à jour d'une connue), choix de la division quand aucune n'est connue, bandeau qui dit ce qu'elle est (`corrigeUneFicheEnAttente`).
- **Elle hérite de la fiche d'origine** : « corriger pour la photo » ne redemande pas la position, la correction n'en a donc pas. `accept_submission` (migration `20261103120000`) reprend **la position de la fiche d'origine**, puis son secteur quand aucune position ne donne la division ; la position de la correction l'emporte quand le relais l'a refaite. L'écran affiche les mêmes valeurs (`heriterDeLOrigine`, calculées par l'adaptateur) ; le faux serveur fait de même. Une correction d'une école déjà créée ne change pas : le campus garde sa position.
- **Le faux serveur est fidèle sur un point** : un relais sans secteur n'a pas de lot (`lot: null`), il ne retombe plus sur le premier lot.

### Les fiches renvoyées au relais (ticket #92)

- **Une fiche renvoyée « à corriger » sort de la file de l'administration : elle attend le relais.** Sans rien pour la montrer, elle « disparaissait » (le fondateur ne retrouvait plus une fiche reçue la veille). « À valider » a un filtre **« Renvoyées »** (en lecture seule, avec « Renvoyée depuis 20 h »), et l'accueil une carte **« Renvoyées aux relais »** (le nombre, depuis quand la plus ancienne) : `src/modele/renvoyees.ts`, sans migration.
- **Côté relais, un refus gardé dans le téléphone est périmé dès que NTanova a décidé** (`refusEstPerime`) : « la photo n'est plus lisible, prévenez NTanova » ne s'affiche plus pour une fiche que NTanova a déjà renvoyée, acceptée ou refusée, et « Réessayer » non plus (il ne peut pas redonner une photo perdue). Tant que la fiche attend NTanova (`a_valider`), le refus reste : la fiche est bien arrivée sans sa photo.

### Le contact ne se perd plus (ticket #94)

Le 03/11, la fiche corrigée d'ESTAM est arrivée sans contact : aucune ligne `prive.direction_contacts`, ni sur l'original ni sur la correction. **Le contact part avant les photos** (`gestesDEnvoi`, `src/modele/envoi.ts` : le relevé, le contact, les photos) : avant, une photo qui ne partait pas ou ne se relisait plus arrêtait la chaîne, et le contact n'arrivait jamais. Une fiche dont le relevé est déjà parti envoie son contact, puis est refusée avec la raison de sa photo ; une fiche dont rien n'est parti ne part pas du tout (elle ne part jamais incomplète). **Une correction redemande la direction quand le contact manque** (`tachesDeLaCorrection`, `contactArrive`) : la direction a été vue et `aContact` est faux sur la fiche et sur celles qu'elle corrige (le contact reste attaché à la fiche qui l'a reçu ; `ReleveRecu.corrigeReleveId` permet de suivre la chaîne). Une ligne gardée avant la mise à jour se lit « on ne sait pas » : dans le doute, on demande. **L'administration lit le contact de la fiche corrigée** quand la correction n'en a pas (`contactReleve` remonte `corrects_submission_id`, sans jamais boucler) et le dit (« arrivé avec la fiche d'origine ») ; « Effacer le contact » s'applique à la fiche qui le porte (`ContactDirection.releveId`). ### Avant d'accepter (ticket #95)

Le 03/11, le fondateur ne savait pas « pourquoi il ne pouvait pas publier » la correction d'ESTAM : le bouton « Accepter » était actif, rien ne bloquait, et l'écran ne le disait pas. **Un encart « Avant d'accepter »** (`avantDAccepter`, `src/modele/acceptation.ts`, une fonction pure) précède les boutons : une ligne par point (photos reçues et vérifiées, position et zone, contact, formations, numéro de l'enseigne, lot de la fiche d'origine), « Rien ne bloque : tu peux accepter » ou « Il reste un choix à faire », et ce que fait « Accepter » : la nouvelle école devient **prête** ; elle ne paraît sur ntanova.com qu'à « Écoles › Publier », puis à la mise en ligne du site. **Seuls la division à choisir, l'institution et l'implantation bloquent** ; le contact, les formations et les photos pas encore vérifiées sont dits comme facultatifs (ni l'acceptation ni la publication ne lisent le contact). **L'en-tête d'une correction ne montre plus le lot de la fiche d'origine** (`ChampsHerites.lotDeLaFicheDOrigine`) : il sert à déduire la division, mais « Lot Essai » sur une correction qui n'est dans aucun lot laissait croire qu'elle ne se publiait pas (la règle du lot d'essai lit le lot de la fiche elle-même). **Un numéro congolais qui n'a pas 9 chiffres après +242** (`numeroCongolaisSuspect`, `src/modele/telephone.ts`) est signalé au relais à la saisie (avertissement, jamais un blocage) et dans l'encart : le numéro d'ESTAM était rangé `+242 0064970301` pour `06 497 03 01`, et il aurait été public. Aucune migration. Les parcours : `tests/parcours/avant-accepter.spec.ts`.

**Le numéro écrit sur l'enseigne se vérifie sur la photo avant d'accepter** (07/11/2026). Ce numéro est publié tel quel, avec un bouton « Appeler », dès que l'école l'est : le 06/11, trois numéros non vérifiés ont paru (deux photos sans aucun numéro, une qui en montrait d'autres ; une première lecture de la photo s'était même trompée d'un chiffre : on agrandit l'image avant de recopier). Dans « À valider », le numéro saisi se lit **à côté de la photo d'enseigne** (« Numéro saisi par le relais : … »), et « Accepter » reste grisé tant que l'administration n'a pas dit, dans le groupe « Numéro écrit sur l'enseigne », **« Je l'ai vérifié sur la photo »** ou **« Il n'est pas sur la photo : ne pas le publier »** (`numeroAConfirmer`, `ceQuiManqueDuNumero`, `numeroPeutEtreRetire`, `ChoixNumero`, dans `src/modele/acceptation.ts` ; la ligne du numéro de « Avant d'accepter » passe à `bloque` tant qu'elle n'a pas répondu). **Pas de migration** : pour une nouvelle école, « pas sur la photo » passe `numeroEnseigne: null` dans les corrections de l'acceptation (la base accepte `sign_phone` nul) ; pour une nouvelle implantation, une mise à jour ou l'ajout de niveaux, `accepterLaFiche` (`AValider.tsx`) remet **après l'acceptation** le numéro que l'école avait avant (lu par `ecoles()` avant d'accepter ; aucun pour une nouvelle implantation) par `modifierEcole`, car le numéro du relais remplace celui de l'école à la mise à jour (`coalesce(r.sign_phone, k.sign_phone)`) ; le faux serveur fait pareil. **Rien à confirmer** quand l'administration a corrigé elle-même le numéro (elle l'a lu), sans numéro saisi, ni sur le lot d'entraînement. **Une correction d'une école déjà créée** ne peut pas le retirer avant l'acceptation (on ne sait pas quel numéro elle a déjà : effacer un numéro vérifié serait pire) : l'écran dit de le retirer ensuite dans « Écoles › Gérer la fiche ». Parcours : `tests/parcours/numero-enseigne.spec.ts` (vérifiés en échec sur l'ancien écran).

Une preuve absente/incomplète/périmée, un autre commit ou dépôt, un contrôle échoué/annulé ne valide rien : retour aux contrôles complets. L’option manuelle `tout_verifier=true` force une nouvelle vérification complète même sur essai. Ouvrir la PR avant de lancer l’essai ; ne pas relancer manuellement une deuxième CI identique. La CI de PR vérifie explicitement le commit de branche, identique à celui testé sur essai. Main est recontrôlé après fusion et avant production.
- **Production et nuit : vérification complète**, sans réutilisation. Un échec de format, types, unitaires, parcours ou SQL bloque le déploiement. Le site fictif partagé entre les lots n’est jamais déployé ; le workflow construit avec les vraies valeurs publiques, puis envoie cet artifact réel.
- Pas de bouton : une mise en ligne planifiée par semaine (le lundi, depuis le 05/11/2026 ; avant : chaque nuit), et un lancement à la main (`gh workflow run mise-en-ligne.yml -f cible=essai`, ou `--ref <branche>` pour essayer une branche sur essai).
- **La nuit n'envoie la production que sur ordre** (décision du fondateur, 02/11/2026, ticket #55) : elle met toujours à jour essai, et n'envoie `ntanova.com` que si la variable GitHub `NUIT_VERS_PRODUCTION` vaut `oui`. Absente, ou autre chose : essai seulement. Un lancement à la main garde son sens (`-f cible=production` envoie la production, sans dépendre de la variable). Un test (`tests/unitaires/mise-en-ligne.test.ts`) évalue la condition dans chaque situation. **Tant que les relais sont en pause, rien ne part chez eux sans un lancement à la main.** **L'administration ne promet donc ni nuit ni heure** pour l'arrivée d'un changement sur `ntanova.com` (« après la prochaine mise à jour du site », vrai dans les deux cas ; ticket #62) : le même test le garde.
- **Chaque bug corrigé arrive avec un test qui échoue sans le correctif** (vérifier qu'il échoue sur l'ancien code). GitHub ne protège pas `main` sur un dépôt privé gratuit : c'est la mise en ligne qui refait tous les contrôles.
- Les valeurs publiques de la construction sont des **variables** GitHub (`vars.PUBLIC_…`), pas des secrets.

## Une tâche = un ticket (protocole du fondateur, 31/10)

Les tâches sont des tickets du projet GitHub n° 29 (« NTanova site · feuille de route »), par priorité. Pour chaque ticket, dans cet ordre :

1. **État des lieux**, en commentaire sur le ticket : ce que le ticket doit produire ; ce qui existe (lu dans le code) ; les problèmes ; les options, avec une recommandation ; l'impact (migrations, écrans, tests, mise en ligne, actions du fondateur) ; ce qui reste hors du ticket ; les décisions attendues.
2. **Le go du fondateur**, tel quel ou modifié. **Rien n'est codé avant.**
3. **Réalisation** : une branche, une PR « Fixes #N », les tests d'abord (un test par bug, vérifié en échec sans le correctif), un essai sur essai.ntanova.com. Un ticket livré en plusieurs PR : les premières disent « Refs #N », seule la dernière dit « Fixes #N » (sinon la première fusionnée ferme le ticket). Essai et production lisent la vraie base : tant qu'aucune école n'y est publiée, ils ne montrent ni liste ni fiche ; pour voir ces écrans, `pnpm captures` (catalogue de test).
4. **Compte rendu** sur le ticket : fait, vérifié, pas vérifié. La fusion : voir « Git ».

**Un regard critique à chaque étape** (consigne du fondateur, 31/10). Il va vite : une consigne peut contenir une erreur de détail, et le travail peut s'éloigner du but sans qu'il le voie. D'abord à l'état des lieux, puis en réalisant, **croiser la maquette, le ticket et le code avec tout le contexte connu** (registre, décisions, autres tickets, état réel de la production) et **dire tout ce qui ne colle pas** : une incohérence dans la maquette, une promesse que le site ne tient pas, une façon de faire qui n'amène pas au résultat attendu. Proposer le correctif ; ne pas recopier une maquette telle quelle.

## Pièges connus

- **Node 24** : faire `nvm use` dans chaque nouveau terminal (Astro 7 exige Node 22.23.4 au moins).
- **`alter domain … add constraint` sans `not valid` échoue pour `niveau`** (« cannot alter type "niveau" because column "field_submissions.levels" uses it ») : la colonne `levels` est un tableau de ce domaine. La CI le voit, puisqu'elle rejoue les migrations.
- **pnpm refuse une version publiée depuis moins de 24 h** (`minimumReleaseAge` dans `pnpm-workspace.yaml`) : c'est voulu.
- **TypeScript reste en 6.0** : `typescript-eslint` et `@astrojs/check` ne prennent pas encore la 7.
- **`astro preview` part en arrière-plan quand un agent le lance** (Astro 7) : `pnpm preview` utilise donc `wrangler dev`, qui sert le site comme Cloudflare.
- **En local, le conteneur des journaux de Supabase (`analytics`) échoue au démarrage** : il est coupé dans `supabase/config.toml`, avec le temps réel et les fonctions edge, inutilisés.
- **Le service worker de `/relais/`** est écrit à la construction (`outils/integration-relais.mjs`, modèle `outils/sw-relais.js`) avec la liste des fichiers à garder ; il n'est pas enregistré sur `localhost` (`pnpm dev`), seulement sur `127.0.0.1` (parcours) et en ligne. **Cette liste, et donc la version du service worker, ne couvrent que ce que `/relais/` charge** (`outils/fichiers-du-relais.mjs` : la page nomme son îlot, son renderer et ses styles, puis chaque fichier nomme les siens, `import()` compris), **pas tout `_astro/`** : une mise en ligne qui ne change que l'administration ou le site public ne change pas la version du relais, donc n'affiche pas « Nouvelle version prête » chez les relais (ticket #62). Une construction où la page du relais ne nomme rien, ou nomme un fichier absent, échoue. Garde-fous : `tests/unitaires/service-worker-relais.test.ts` et `tests/parcours/service-worker.spec.ts` (tout ce que le relais charge en parcourant ses écrans doit être dans la liste, sinon il manquerait hors ligne).
- **Un parcours qui agit juste après un message de succès peut agir avant que l'écran se soit rafraîchi** : la ligne est remise à zéro et le formulaire ouvert se referme (« Publier », puis « Retirer du site »). De même, ne pas couper le réseau avant que ce que l'écran doit garder soit affiché (le lot). Attendre l'état final (« Publiée », le nom du lot) avant d'agir. Pour le vérifier : ralentir le faux serveur (`localStorage['ntanova-faux-latence']`, en millisecondes) et voir l'ancien test échouer.
- **`react-hooks` refuse un `setState` direct dans un effet** : lancer l'action dans l'effet, et changer l'état dans ses rappels (voir `lancer` dans `src/app/relais/App.tsx`).
- **Une table ou une vue créée APRÈS le `revoke all` d'une migration garde les droits par défaut de Supabase** (écrire et supprimer compris) en local et dans la CI, pas en ligne : retirer ses droits, objet par objet, juste avant de donner ceux qu'il faut. Le banc (`supabase/portabilite/shim-supabase.sql`) imite ces droits par défaut, et aussi `storage.protect_delete` : un test qui supprime dans `storage.objects` pose d'abord `set local storage.allow_delete_query = 'true'`, comme le fait l'API du stockage. Sans cela, le banc est vert et la tâche `base` de la CI rouge (arrivé le 02/11 : sept vues).
- **Dans `src/`, écrire « ticket 114 », jamais « ticket #114 »** : `pnpm couleurs` lit `#114` comme une couleur hexadécimale et refuse le fichier (les tests, les outils et `jetons.css` ne sont pas lus).
- Les règles `no-restricted-imports` d'ESLint ne se cumulent pas : pour un fichier, seul le dernier bloc qui le vise compte. Chaque bloc de `frontiere()` donne donc la liste complète de son dossier.
